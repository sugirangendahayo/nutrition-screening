# 3. Shared Preprocessing

Both models contain their own preprocessing pipeline.

The preprocessing is:

```text
Numeric:
CAGE
    ↓
SimpleImputer(strategy="median")
    ↓
StandardScaler

Categorical:
all other input variables
    ↓
SimpleImputer(strategy="most_frequent")
    ↓
OneHotEncoder(handle_unknown="ignore", sparse_output=False)
```

This means Flask should **not recreate a separate preprocessing implementation** if the saved pipeline is used directly.

The correct architecture is:

```text
Raw frontend input
        ↓
Flask validation
        ↓
Pandas DataFrame with the exact raw feature names
        ↓
Saved Pipeline
        ↓
Preprocessor
        ↓
Classifier
        ↓
Prediction / probability
```

Do not manually one-hot encode these fields in the frontend.

Do not manually scale `CAGE` in the frontend.

Do not apply another scaler before calling the saved pipeline.

# 7. Individual Prediction Explanation

The project requirement is to show feature importance/explanation after a prediction.

Do this carefully.

There is an important distinction:

### Global feature importance

```text
Which predictors are generally important to the model?
```

### Local explanation

```text
Which predictors contributed to THIS child's prediction?
```

The `feature_importances_` values above are global.

If a technically appropriate local explanation method such as SHAP can be applied reliably to the actual model, prefer that for the individual result.

Otherwise, label the UI honestly as:

```text
Model Feature Importance
```

rather than:

```text
Why this child was classified this way
```

Never fabricate percentages.

# 9. Important Compatibility Note

The artifacts were saved using scikit-learn 1.6.1.

The saved pipelines contain scikit-learn objects including:

- SimpleImputer
- StandardScaler
- OneHotEncoder
- ColumnTransformer
- Pipeline

Therefore the backend environment should initially use a compatible scikit-learn version, preferably:

```text
scikit-learn==1.6.1
```

Do not blindly upgrade scikit-learn to a newer major/minor version without testing the artifacts.

The underweight model also depends on XGBoost. The exact training-time XGBoost version should be confirmed with the colleague/training environment before pinning a production version.

The model artifacts should be tested after installing the intended backend dependencies.

# 10. Safe Model Loading

The `.pkl` files should only be loaded as trusted project artifacts.

Do not load arbitrary user-uploaded pickle files.

A pickle/joblib artifact can execute arbitrary Python code during deserialization, so model uploads must not be exposed as an unrestricted user feature.

---

# 11. Integration Checklist for Claude

When integrating these models:

1. Copy the original `.pkl` files into the backend model directory.
2. Do not modify the binary files.
3. Pin/use compatible Python ML dependencies.
4. Load them with Joblib.
5. Verify the pipeline loads successfully in the backend environment.
6. Build the input DataFrame with the exact 20 raw feature names.
7. Preserve the expected input types.
8. Let each saved Pipeline perform its own preprocessing.
9. Call `predict()`.
10. Call `predict_proba()` where supported.
11. Verify the meaning of class `0` and class `1` from the training code/labels.
12. Add model version metadata.
13. Add tests with known valid inputs.
14. Only then connect the result to the React UI.
